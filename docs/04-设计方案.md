---

## 1. 设计原则

1. **先规则，后模型。** 能用确定性公式算出来的，不引入模型；模型只在「无历史、强波动」的长尾场景作为兜底，且必须输出置信度。
2. **不可逆动作前必有确定性校验。** 下发单据、生成调拨单属于不可逆动作，必须在写入前完成库存上限、效期、权限、重复请求四类校验。
3. **例外管理而非全量复核。** 计划员只处理「低置信 / 缺数据 / 冲突 / 越权」四类例外，其余自动流转，但保留逐单追溯与一键接管。
4. **每个输出可追溯。** 每条建议必须能回答：用了哪份数据快照（版本号）、命中哪条规则（规则 ID）、置信度多少、谁确认（姓名 + 时间）。
5. **不替代底座系统。** 补货协同层只做决策与协同，读写通过接口，不复制 POS/WMS/ERP 的主数据职责。
6. **降级优先于失败。** 接口超时或数据缺失时，系统必须能退回「手工台账」模式继续工作，而不是卡死。

---

## 2. 方案比较与选择

| 维度 | A. 纯人工优化（加人/加表/加培训） | B. 规则引擎 + 例外复核（推荐） | C. 预测模型 + 自动补货 |
|---|---|---|---|
| 解决 OP-1 信号数字化 | 部分（仍是微信群） | **是** | 是 |
| 解决 OP-2 算量一致性 | 弱（依赖个人） | **是（公式统一）** | 是 |
| 处理时长 | 4.2h → 约 3h（-29%） | **4.2h → ≤40min（-84%）** | 4.2h → ≤30min |
| 返工次数 | 1.7 → 1.4 | **1.7 → ≤0.5** | 1.7 → ≤0.3 |
| 投入 | 约 8 万/年（增 1 名计划员） | **30.1 万（试点）/ 65.6 万（标准）** | 125.4 万（C 档：数据治理 + 模型 + VMI） |
| 失败可见性 | 低（问题继续潜伏） | **高（每单可查）** | 中（模型误差难归因） |
| 可撤销性 | 高 | **高（建议可改可驳）** | 低（自动下单难回滚） |
| 数据前提 | 无 | 日销 + 库存 + 在途（已有） | 需 12 个月促销标记 + 天气 + 竞品 |
| 结论 | 治标 | **选定** | 暂缓（P2，试点达标后再评估） |

**为什么需要系统而不是「再招一个人」**：A 方案不改变「信号—口径—单据」三段手工结构，人员流动后问题复现；且 48 店扩张到 70 店时，人力线性增长，系统不增长。

**为什么现在不做模型**：饭团案例（EV-04）显示新品无历史时人工估值偏差 3.5 倍，模型在无促销标记的情况下同样无解；先解决「有数据、有规则、有单据」的问题，模型才有落点。

**试点排除项**：冷冻品类（温度链要求高）、供应商 VMI、自动审批、写入门店系统、促销排期改造、跨区域（苏州↔上海）调拨。

## 3. 系统架构

```
┌──────────────────────────────────────────────────────────────┐
│  交互层   门店端（手机 H5）     计划员协同台（Web）   看板      │
├──────────────────────────────────────────────────────────────┤
│  决策层   缺货识别 → 建议量引擎 → 约束校验 → 例外路由          │
│           ↑规则库(版本化)   ↑置信度   ↑硬校验(效期/上限/权限)   │
├──────────────────────────────────────────────────────────────┤
│  协同层   补货单 / 调拨单 / 到货确认 / 异常单 / 审计日志        │
├──────────────────────────────────────────────────────────────┤
│  数据层   数据快照(vYYYYMMDD-HHmm) → 计算字段 → 指标口径层      │
├──────────────────────────────────────────────────────────────┤
│  接口层   POS 日销 · WMS 库存与在途 · 商品主数据（只读）        │
└──────────────────────────────────────────────────────────────┘
```

**分层职责**

| 层 | 职责 | 不做什么 |
|---|---|---|
| 接口层 | 每日 06:30 拉取 T-1 日销、库存、在途、效期；失败重试 3 次后告警 | 不写回任何业务系统 |
| 数据层 | 生成快照版本号，统一口径（库存 = 可用库存，不含锁定与残损） | 不做清洗外的业务判断 |
| 决策层 | 算建议量、算置信度、跑硬校验、决定是否转例外 | 不直接下发单据 |
| 协同层 | 生成单据、记录确认人、写审计 | 不修改上层建议（只记录改量理由） |
| 交互层 | 上报、审核、确认、查看 | 不做业务计算 |

## 4. 核心算法（建议量与约束）

### 4.1 基础公式

```
日均销量 d      = 近 7 日销量之和 / 有效销售天数（剔除闭店日与全品类缺货日）
安全库存 SS     = d × (提前期 L + 复核周期 R) × 安全系数 k
目标库存 T      = SS + d × 陈列覆盖天数 C
建议量 Q0       = T − 可用库存 − 在途 + 已确认未到货
建议量 Q        = 向上取整到最小订货单位 MOQ 的整数倍，且 ≥ MOQ（若 Q0 > 0）
```

参数（试点期取值，可按品类覆盖）：

| 参数 | 常温 | 冷藏 | 说明 |
|---|---|---|---|
| 提前期 L | 2 天 | 1 天 | 门店至 DC 的实际到货间隔（EV-05） |
| 复核周期 R | 1 天 | 1 天 | 每日一次 |
| 安全系数 k | 1.0 | 1.3 | 冷藏波动大、缺货敏感 |
| 陈列覆盖 C | 3 天 | 2 天 | 避免「有库存但货架空」 |
| MOQ | 6 | 4 | 按箱规 |

### 4.2 硬约束（不可逆动作前的确定性校验）

| 校验 | 触发条件 | 动作 | 错误码 |
|---|---|---|---|
| 效期约束 | 剩余保质期 < L + 7 天 | 禁止补货；若其他店有需求则转「调拨出」建议 | `E_SHELF_LIFE` |
| 库存上限 | 补后库存 > d × 30 天 | 截断至上限并标注「已达周转上限」 | `W_STOCK_CAP` |
| 权限校验 | 非本店 SKU / 非授权品类 | 拒绝并记录越权尝试 | `E_SCOPE` |
| 重复请求 | 同店同 SKU 24 小时内已有在途单据 | 合并提示，不重复生成 | `E_DUPLICATE` |
| 数据新鲜度 | 快照超过 36 小时 | 阻断自动建议，退回手工模式 | `E_STALE` |
| 缺数据 | 近 7 日有效销售天数 < 3 | 转人工，置信度标 `low` | `W_SPARSE` |

### 4.3 置信度与例外路由

```
CV = 近 7 日销量标准差 / 日均销量
confidence = high   if CV ≤ 0.5 且有效天数 ≥ 6
             medium if CV ≤ 0.9 且有效天数 ≥ 4
             low    其余
路由：high → 批量流转（计划员可抽检）
      medium → 逐单确认（默认值可改）
      low → 强制人工填写（必须写理由），并记入评估集
```

**调拨评分**（OP-3）：

```
score = 0.35×可调出量富余度 + 0.25×效期紧迫度 + 0.20×距离得分 + 0.10×同区 + 0.10×装载匹配
约束：调出后本店库存不得低于 SS；冷藏跨区调拨需叶书确认
```

## 5. 数据契约

### 5.1 核心实体

| 实体 | 关键字段 | 主键 | 来源 |
|---|---|---|---|
| store | store_id, name, city, format, shelf_capacity | store_id | 主数据 |
| sku | sku_id, name, category, temp_zone, moq, case_size, shelf_life_days | sku_id | 主数据（傅景） |
| sales_daily | store_id, sku_id, biz_date, qty, amount | (store_id, sku_id, biz_date) | POS（EV-01） |
| inventory | store_id, sku_id, snapshot_id, on_hand, locked, damaged, batch_expiry | (store_id, sku_id, snapshot_id) | WMS（EV-05） |
| in_transit | store_id, sku_id, order_id, qty, eta_date | order_id | WMS |
| replenishment | req_id, store_id, sku_id, suggest_qty, final_qty, rule_id, confidence, snapshot_id, status, created_by, approved_by, approved_at, reason | req_id | 本系统 |
| transfer | transfer_id, from_store, to_store, sku_id, qty, score, approved_by, status | transfer_id | 本系统 |
| audit | event_id, actor, action, object, before, after, at, snapshot_id | event_id | 本系统 |

### 5.2 关键字段规则

- `snapshot_id` 格式 `vYYYYMMDD-HHmm`，全链路必带，用于「版本正确率」核算。
- `suggest_qty` 与 `final_qty` 分开存，**改量必须写 `reason`**，用于返工分析。
- `confidence` 仅三档枚举，禁止出现「0.87」这类无口径小数。
- 金额与数量均为整数（分 / 件），避免浮点误差。
- 删除一律软删除（`deleted_at`），审计表只增不改。

### 5.3 权限矩阵

| 角色 | 日销 | 库存/在途 | 建议量 | 下发单据 | 调拨审批 | 规则参数 |
|---|---|---|---|---|---|---|
| 门店店长（林亦舟） | 本店只读 | 本店只读 | 本店只读 | 提交申请 | 无 | 无 |
| 补货计划员（唐映秋） | 全区只读 | 全区只读 | 读写 | **批准/改量** | 发起 | 无 |
| 区域物流（叶书） | 只读 | 全区只读 | 只读 | 执行 | **批准** | 无 |
| 商品与损耗（傅景） | 只读 | 只读 | 只读 | 无 | 无 | 效期/MOQ |
| 数据工程（秦芮） | 无业务权限 | 快照管理 | 无 | 无 | 无 | 接口与快照 |
| 运营总监（顾明岚） | 全区只读 | 全区只读 | 只读 | 无 | 仲裁 | 预算与范围 |

## 6. 人工复核节点（不可省略）

| 节点 | 位置 | 谁 | 触发 | 记录 |
|---|---|---|---|---|
| N1 上报确认 | 门店上报后 | 店长本人 | 每次上报 | 上报人、时间、照片（可选） |
| N2 建议复核 | 下发前 | 唐映秋 | medium/low 置信、改量、超上限 | 原建议、最终值、理由 |
| N3 调拨审批 | 调拨单生成前 | 叶书 | 所有跨店调拨 | 评分明细、审批意见 |
| N4 到货确认 | 收货时 | 店长 | 每次到货 | 实收数、差异、照片 |
| N5 异常裁决 | 差异/越权/超时 | 唐映秋 + 叶书 | `E_*` 错误码 | 处置结论、是否补单 |

**阻断原则**：N2 未完成 → 不得生成补货单；N3 未完成 → 不得生成调拨任务；`E_SHELF_LIFE` / `E_SCOPE` / `E_STALE` → 系统直接拒绝，人工无权重写（只能改数据源后重跑）。

## 7. 接口契约（3 个）

| 接口 | 方向 | 频率 | 关键字段 | 失败处理 |
|---|---|---|---|---|
| `GET /pos/sales?date=` | 只读 | 每日 06:30 | store_id, sku_id, qty, amount | 重试 3 次 → 告警 → 沿用 T-2 数据并标 `E_STALE` |
| `GET /wms/inventory?snapshot=` | 只读 | 每日 06:40 | on_hand, locked, in_transit, batch_expiry | 同上；无库存数据直接阻断自动建议 |
| `GET /mdm/sku` | 只读 | 每周一 | moq, case_size, shelf_life_days, temp_zone | 用缓存 + 变更告警 |

**接口替身**：试点第 1–2 周用「导出文件 + 定时导入」替代实时接口，字段与线上一致，验证契约本身（合成适配与真实接口的差距：真实接口有网络抖动、限流、字段缺失，需在阶段 5 记录）。

## 8. 评估计划

### 8.1 评估集（覆盖 5 类场景，共 60 例）

| 类型 | 例数 | 例子 | 失败成本 |
|---|---|---|---|
| 正常 | 20 | 常规 SKU，7 日稳定销量 | 低 |
| 边界 | 12 | 新品 3 天历史、促销日、闭店日、MOQ 临界 | 中 |
| 对抗 | 8 | 销量突增 5 倍、促销叠加、竞品断货引流 | 高 |
| 权限 | 10 | 跨店改量、非授权品类、无审批下发 | **最高（合规）** |
| 故障 | 10 | 快照过期、接口超时、重复提交、效期边界 | 高 |

### 8.2 通过标准

| 指标 | 阈值 | 测量方式 |
|---|---|---|
| 建议量偏差 | 与计划员最终值偏差 ≤ 20% 的订单占比 ≥ 80% | 试运行 4 周对比 |
| 硬约束漏放 | **0 例**（效期/越权/重复） | 审计日志逐条 |
| 异常路径完整 | 5 类 `E_*` 全部可复现并可转人工 | 演练记录 |
| 处理时长 | 中位数 ≤ 40 分钟 | 系统时间戳 |
| 版本正确率 | ≥ 96% | 下发单 vs 到货确认 |
| 采用率 | ≥ 70% | 门店确认率 |

### 8.3 停止条件（任一触发即停，不追加投入）

1. 第 6 周结束仍无法稳定获得「库存 + 在途」日快照。
2. 出现 1 例未经 N2/N3 确认即下发单据。
3. 处理时长连续 3 周无改善。
4. 门店采用率 < 40% 且访谈确认「比微信群更麻烦」。
