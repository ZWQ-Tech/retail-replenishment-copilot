## 1. 背景

拾光连锁 48 家门店「一边缺货一边积压」：爆款缺货率 12%、库存周转 48 天，目标分别为 5% 以下与 35 天（`retail-f00`）。调研收敛后发现，**最值得先做的不是销量预测，而是「可售库存口径与缺货标识治理」**——三处已确证瓶颈：

1. **有货 ≠ 可售**：货在后仓但货架没补，系统仍算有库存，账实差异平均 8%（`retail-f10`、`retail-f12`）。
2. **缺货截断误读**：销量为零可能是缺货截断，不是没人买（`retail-f31`）。
3. **约三成延迟补货是配送排队**，不是预测问题（`retail-f51`）。

若口径不统一，预测输入本身失真，补货建议不可信。因此本方案先做「口径治理 + 规则化补货 + 兜底审计」的最小闭环，预测模型后置。

## 3. 设计原则

1. **先规则，后模型**：能用确定性公式算的不引入模型；模型只在「无历史、强波动」长尾场景兜底，且输出置信度。
2. **不可逆动作前必有确定性校验**：下发单据、生成调拨单前必须完成库存上限、效期、权限、重复、新鲜度五类校验。
3. **例外管理而非全量复核**：计划员只处理「低置信 / 缺数据 / 冲突 / 越权」四类例外，其余自动流转。
4. **每个输出可追溯**：每条建议能回答「用了哪份快照（版本号）、命中哪条规则（规则 ID）、置信度多少、谁确认（姓名+时间）」。
5. **兜底优先于推进**：临时促销、缺货截断、账实不一致、依据缺失或系统不可用时，必须停止自动建议并标明原因、接手人、人工确认时间（`retail-f44`）。
6. **不替代底座系统**：只做决策与协同，通过接口读写，不复制 POS/WMS/ERP 主数据职责。

## 5. 系统架构

```
┌──────────────────────────────────────────────────────────────┐
│  交互层   门店端（手机 H5）     计划员协同台（Web）   看板      │
├──────────────────────────────────────────────────────────────┤
│  决策层   缺货识别 → 建议量引擎 → 约束校验 → 例外路由          │
│           ↑规则库(版本化)  ↑置信度  ↑硬校验(效期/上限/线路容量) │
├──────────────────────────────────────────────────────────────┤
│  协同层   补货单 / 调拨单 / 到货确认 / 异常单 / 审计日志        │
├──────────────────────────────────────────────────────────────┤
│  数据层   数据快照(vYYYYMMDD-HHmm) → 计算字段 → 指标口径层      │
├──────────────────────────────────────────────────────────────┤
│  接口层   POS 日销 · WMS 库存与在途 · 商品主数据（只读）        │
└──────────────────────────────────────────────────────────────┘
```

| 层 | 职责 | 不做什么 |
|---|---|---|
| 接口层 | 每日 06:30 拉取 T-1 日销、库存、在途、效期；失败重试 3 次后告警 | 不写回任何业务系统 |
| 数据层 | 生成快照版本号，统一口径（库存 = 可售库存，区分账面 onHand 与可售 sellable） | 不做清洗外的业务判断 |
| 决策层 | 算建议量、算置信度、跑硬校验、决定是否转例外 | 不直接下发单据 |
| 协同层 | 生成单据、记录确认人、写审计 | 不修改上层建议（只记录改量理由） |
| 交互层 | 上报、审核、确认、查看 | 不做业务计算 |

## 6. 核心算法（建议量与约束）

### 6.1 基础公式

```
日均销量 d      = 近 7 日销量之和 / 有效销售天数（剔除缺货截断日）
安全库存 SS     = d × (提前期 L + 复核周期 R) × 安全系数 k
目标库存 T      = SS + d × 陈列覆盖天数 C
建议量 Q0       = T − 可售库存 − 在途
建议量 Q        = 向上取整到整箱的整数倍，且 ≥ 起订量 MOQ（若 Q0 > 0）
```

> 关键变化（相对旧版）：缺口计算用「**可售库存**」而非「**账面库存**」，对齐 retail-f10/f12 的「有货 ≠ 可售」。

### 6.2 硬约束（不可逆动作前的确定性校验）

| 校验 | 触发条件 | 动作 | 错误码 |
|---|---|---|---|
| 效期约束 | 剩余保质期 < 提前期 + 7 天 | 禁止补货；转「调拨出」建议 | `E_SHELF_LIFE` |
| 线路容量 | 建议量 > 本店线路容量 | 阻断，拆单或人工确认 | `E_LINE_CAP` |
| 库存上限 | 补后可售 > d × 30 天 | 截断至上限并标注 | `W_STOCK_CAP` |
| 权限校验 | 非本店 SKU / 非授权品类 | 拒绝并记录越权尝试 | `E_SCOPE` |
| 重复请求 | 同店同 SKU 24 小时内已有在途单 | 合并提示，不重复生成 | `E_DUPLICATE` |
| 数据新鲜度 | 快照超过 36 小时 | 阻断自动建议，退回手工 | `E_STALE` |
| 缺数据 | 近 7 日有效销售 < 3 天 | 转人工，置信度标 `low` | `W_SPARSE` |
| 缺货截断 | 近 14 日存在缺货截断 | 需求可能被低估，标告警 | `W_STOCKOUT` |
| 促销未回传 | 促销版本未同步 | 建议量按促销期算，标告警 | `W_PROMO` |

### 6.3 置信度与例外路由

```
CV = 近 7 日销量标准差 / 日均销量
confidence = high   if CV ≤ 0.5 且有效天数 ≥ 6
             medium if CV ≤ 0.9 且有效天数 ≥ 4
             low    其余
路由：high → 批量流转（计划员可抽检）
      medium → 逐单确认（默认值可改）
      low → 强制人工填写理由，并记入评估集
```

**兜底触发（retail-f44）**：遇临时促销未回传、缺货截断、可售与账面不一致、依据缺失、系统不可用，停止自动建议，标明原因、接手人与人工确认时间。

**调拨评分**：

```
score = 0.35×可调出富余度 + 0.25×效期紧迫度 + 0.20×距离得分 + 0.10×同区 + 0.10×装载匹配
约束：调出后本店可售不得低于安全库存；跨店调拨需叶书（区域物流）审批
```

## 8. 项目全周期实施规划

| 阶段 | 周 | 交付 | 关键动作 |
|---|---|---|---|
| 对接与契约 | 1–2 | 数据契约、接口替身、权限矩阵 | 8 店 50 SKU 近 90 天 CSV 导出、人工标注缺货截断、核对账实差异 |
| 构建闭环 | 3–4 | 上报、建议引擎、复核、下发、审计 | 规则引擎 + 例外复核 + 兜底审计 + 门店可见到货 |
| 并行试点 | 5–10 | 8 店实跑、异常演练、每周复盘 | 历史回放 → 并行试点，现有人工流程不直接关掉 |
| 对照评估 | 11–12 | 前后对照、缺陷闭环、上线建议 | 缺货率/周转/报废三指标按周对比，任一恶化即暂停 |

**关键里程碑**：
- 第 4 周末：MVP 闭环可用（上报→建议→复核→下发→收货→审计）
- 第 6 周末：历史回放验证建议量全部落在整箱与线路容量内
- 第 12 周末：6 周试点数据完整，产出上线建议

**停止条件（任一触发即停，不追加投入）**：
1. 第 6 周结束仍无法稳定获得「库存 + 在途」日快照。
2. 出现 1 例未经计划员确认即下发单据。
3. 缺货率 / 周转 / 报废任一指标恶化且无改善趋势。
4. 门店采用率 < 40% 且访谈确认「比微信群更麻烦」。
