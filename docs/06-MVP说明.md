# 06 · MVP 说明与演示脚本

> 代码目录：`mvp/`　｜　**在线直接打开**：https://zwq-tech.github.io/retail-replenishment-copilot/mvp/
> 本地运行：双击 `mvp/index.html`，或 `python3 -m http.server` 后访问 `/mvp/`
> 技术栈：原生 HTML + CSS + JavaScript（无框架、无构建、无后端），数据存浏览器 localStorage
> 数据：确定性生成的合成数据（48 店 × 18 SKU × 14 天日销），刷新结果一致

---

## 1. 为什么是「这个」最小闭环

`01-业务挖掘.md` 的结论是：瓶颈在「信号—算量—下发」三段手工环节，不在预测精度。因此 MVP 只做这条链路上最小的可运行闭环：

```
门店缺货上报 → 建议量引擎 → 硬约束校验 → 计划员例外复核 → 下发 / 调拨 → 扫码收货 → 指标 + 审计
```

不做：销量预测模型、供应商 VMI、自动审批、写回真实系统、冷冻品类。这与 `04-设计方案.md` 第 2 节的「试点排除项」一致。

## 2. 五个页面在解决什么

| 页面 | 角色 | 解决的问题 | 对应证据 |
|---|---|---|---|
| 指标看板 | 顾明岚 / 全体 | 五项过程指标与人工期基线同口径对照，问题能定位到环节 | EV-13 周会三口径 |
| 缺货上报 | 林亦舟（店长） | 把微信群口语消息变成结构化的 SKU-店-时间信号，3 步完成 | EV-03 38% 消息无数量 |
| 建议审核 | 唐映秋（计划员） | 只审例外；改量必须写理由，理由进入返工分析 | EV-04 v3/v5/v7 版本混乱 |
| 跨店调拨 | 叶书（区域物流） | 用 5 因子评分替代电话协调，审批留痕 | EV-09 调拨靠人情 |

| 审计日志 | 全部 | 每条动作带操作人、前后值、快照版本 | FDE 可追溯要求 |

## 3. 规则引擎（与设计方案逐条对应）

### 3.1 建议量

```
日均销量 d   = 近 7 日销量之和 ÷ 7（剔除闭店日）
安全库存 SS  = d × (提前期 L + 复核周期 R) × 安全系数 k
目标库存 T   = SS + d × 陈列覆盖天数 C
建议量 Q0    = T − 可用库存 − 在途
Q            = 按箱规向上取整，且不低于起订量 MOQ
```

| 品类 | L | R | k | C |
|---|---|---|---|---|
| 常温 | 2 天 | 1 天 | 1.0 | 3 天 |
| 冷藏 | 1 天 | 1 天 | 1.3 | 2 天 |
| 冷冻 | 2 天 | 1 天 | 1.1 | 2 天 |

### 3.2 置信度

`CV = 近 7 日销量标准差 ÷ 日均`；`high`：CV ≤ 0.5 且有效天数 ≥ 6；`medium`：CV ≤ 0.9 且 ≥ 4；其余 `low`。

### 3.3 硬约束（6 条，全部可在页面上复现）

| 错误码 | 触发场景（演示位置） | 表现 |
|---|---|---|
| `E_SHELF_LIFE` | 上海·社区01店「三明治 火腿芝士」（剩余保质期 2 天） | 复选框置灰、建议量 0、标签提示改走调拨 |
| `W_STOCK_CAP` | 积压门店（如上海·社区13店） | 建议量被截断到 30 天周转上限 |
| `W_SPARSE` / `W_NEW` | 上海·社区01店「关东煮 鱼丸」（新品） | 置信度降为 low，规则切到 `R-SS-02` 品类均值兜底 |
| `E_DUPLICATE` | 同店同 SKU 已有待复核单时再次提交 | 建议量 0 并提示重复 |
| `E_STALE` | 快照超 36 小时（演示中可在 `settings.stale` 打开） | 阻断自动建议，退回手工 |
| `E_SCOPE` | 跨城调拨且非上海区域 | 前端直接阻断并记录 |

### 3.4 调拨评分

```
score = 0.35×富余度 + 0.25×效期紧迫 + 0.20×距离 + 0.10×同城 + 0.10×装载匹配
约束：调出后本店库存不得低于安全库存
```

## 4. 演示脚本（约 5 分钟，可按顺序念）

1. **看板**：5 个指标当前值全为「—」，因为本次会话还没有系统单据；卡片下方「人工期基线」取自 26 单历史样本（238 分钟、1.62 次/单、85.7%）。与 `01-业务挖掘` 的 96 单全量样本（4.2 小时 / 1.7 次 / 82%）略有差异，因为这里只取了子集，口径定义完全一致。
2. **缺货上报**：门店默认「上海·社区01店」（试点店，缺货最多）。系统已识别 6 条：其中「三明治 火腿芝士」被 `E_SHELF_LIFE` 拦截（剩余保质期 2 天，复选框置灰）、「关东煮 鱼丸」是新品低置信 `W_NEW`。勾选 3 条 → 提交上报。
3. **建议审核**：第 1 单把建议量改掉并填理由（例如「周末园区团建，门店临时加场」）→ 通过下发；其余按建议直接通过。注意改量不填理由会被拦，理由与改量幅度都会进返工分析。
4. **跨店调拨**：审核通过后，DC 库存不足的单会出现在这里（演示数据里饭团 DC 仅 9 件、关东煮仅 6 件，天然触发）。点「查看调拨建议」→ 按 5 因子评分给出 Top3（同城、效期更紧迫的门店排在前面）→ 审批生成调拨单。
5. **到货确认**：自上而下依次收货，默认按应到数量预填；把某一行实收改成少于应到，会立刻开出「数量差异」异常单，并拉低「单据版本正确率」——`01` 里 82% 的差距就是这么来的。
6. **回到看板**：处理时长从 238 分钟掉到「<1 分钟」，返工从 1.62 次/单降到 0.3 次/单左右，版本正确率从 85.7% 升到 100%，人工复核成本从 63 元/单降到 14 元/单。

> 具体小数会随你处理几单、改了几次量而变，这是刻意的：指标由单据时间戳和改量次数实时算出，不是写死的展示值。样本少于 20 单时波动大，只用于看变化方向。
7. **审计日志**：每一步都有操作人、前后值、快照版本，可直接回答「谁在什么时候把数量从 30 改成 96、为什么」。

> 重置：右上角「重置演示数据」清空会话，回到初始样本。

## 6. 代码结构与可验证性

```
mvp/
├── index.html   结构（6 个视图容器 + 侧边导航）
├── style.css    样式（浅色、双列布局、移动端折叠）
├── data.js      数据层：确定性生成 48 店 / 18 SKU / 14 天日销 / 库存 / 在途 / DC
├── engine.js    决策层：纯函数（baseline / detectShortage / suggest / rankTransfers / kpi）
└── app.js       交互层：状态管理、视图渲染、事件、审计
```

`engine.js` 无 DOM 依赖，可直接用 Node 验证：

```bash
node -e "require('./data.js');require('./engine.js');
const D=RC_DATA,E=RC_ENGINE;
console.log(E.suggest(D,'ST001','S001',{}));"
```

已用 Puppeteer 跑过一次完整端到端：上报 4 单 → 改量下发 → 调拨审批 → 3 单收货 → 看板与审计更新，控制台零报错。

## 7. 与真实系统的差距（已知限制，必须写明）

| 差距 | 影响 | 真实项目需要 |
|---|---|---|
| 数据为合成样本，存 localStorage | 无法多端协同、无并发控制 | 真实 POS/WMS 接口 + 服务端数据库 |
| 无登录与角色鉴权 | 权限矩阵只是界面层演示 | 统一身份 + RBAC + 操作审计入库 |
| 建议量用近 7 日简单均值，无促销/天气因子 | 促销期和大促前后偏差大 | 促销日历、天气、节假日特征 |
| 无预测模型 | 新品与突变需求仍靠兜底规则 | C 档范围（`05-报价单.xlsx`） |
| 调拨不含车辆装载与线路优化 | 可能增加物流成本 | 与 TMS 打通或人工二次确认 |
| 异常单只在本地生成 | 不进入工单系统 | 对接客服/工单平台 |

这些差距在 `04-设计方案.md` 第 10 节风险表中均有对应缓解措施，不属于「演示后才发现」的问题。
