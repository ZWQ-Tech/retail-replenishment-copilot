# 06 · MVP 说明与演示脚本

> 代码目录：`mvp/`　｜　**在线直接打开**：https://zwq-tech.github.io/retail-replenishment-copilot/mvp/
> 本地运行：双击 `mvp/index.html`，或 `python3 -m http.server` 后访问 `/mvp/`
> 技术栈：原生 HTML + CSS + JavaScript（无框架、无构建、无后端），数据存浏览器 localStorage
> 数据：确定性生成的合成数据（**8 店 × 50 常温 SKU × 14 天日销**，试点口径），刷新结果一致

---

## 1. 为什么是「这个」最小闭环

`01-业务挖掘.md` 的结论是：瓶颈在「口径—信号—算量—下发」这段手工链条，不在预测精度。因此 MVP 只做这条链路上最小的可运行闭环：

```
门店缺货上报 → 建议量引擎 → 硬约束校验 → 计划员例外复核 → 下发 / 调拨 → 扫码收货 → 指标 + 审计
```

不做：销量预测模型、供应商 VMI、自动审批、写回真实系统、冷冻/冷藏品类。这与 `04-设计方案.md` 第 2 节的「试点排除项」一致。

**核心口径**（对齐 34 条事实）：

| 口径 | 事实 | 在 demo 中的体现 |
|---|---|---|
| 有货 ≠ 可售 | retail-f10 / f12 | 库存分「账面 onHand / 可售 sellable」两个字段，缺货识别基于可售 |
| 缺货截断 | retail-f31 | 销量为零但带截断标记 → 提示「需求被低估」，置信度降为 low |
| 促销变价 | retail-f11 / f21 | 促销版本随建议传递，未回传则标 `W_PROMO` 警示 |
| 整箱/起订量/线路容量 | retail-f20 / f50 | 建议量按箱规取整、不低于 MOQ、不超线路容量 |
| 30% 延迟是配送排队 | retail-f51 | 看板「延迟归因」把延迟拆成排队/预测/其它 |
| 兜底 + 审计可重建 | retail-f44 / f45 | `shouldFallback` 判定 + 每条动作带操作人/前后值/快照版本 |

## 2. 页面在解决什么

产品级 demo 共 **9 个视图**（1 个总览 + 7 个工作台/追溯页 + 规则参数），顶部有「演示引导」「自动滚动」「重置」三个演示辅助按钮。

| 视图 | 角色 | 解决的问题 | 对应证据 |
|---|---|---|---|

| 指标看板 | 顾明岚 / 全体 | 缺货率/周转/账实差异/报废与人工期基线同口径对照 | retail-f00 / f42 |

## 3. 规则引擎（与设计方案逐条对应）

### 3.1 建议量

```
日均销量 d   = 近 7 日销量之和 ÷ 7
安全库存 SS  = d × (提前期 L + 复核周期 R) × 安全系数 k
目标库存 T   = SS + d × 陈列覆盖天数 C
建议量 Q0    = T − 可售库存 − 在途        ← 用「可售」而非「账面」（retail-f10）
Q            = 按整箱向上取整，且不低于起订量 MOQ
```

### 3.2 置信度

`CV = 近 7 日销量标准差 ÷ 日均`；`high`：CV ≤ 0.5 且有效天数 ≥ 6；`medium`：CV ≤ 0.9 且 ≥ 4；其余 `low`。缺货截断或新品历史不足时强制降为 `low`，并切换到品类均值兜底（`R-SS-02`）。

### 3.3 硬约束（6 类，全部可在页面上复现）

| 错误码 | 触发场景 | 表现 |
|---|---|---|
| `E_SHELF_LIFE` | 剩余保质期 < 提前期 + 7 天 | 禁止补货，建议调拨出 |
| `W_STOCK_CAP` | 补后库存超 30 天周转上限 | 建议量截断到上限 |
| `E_LINE_CAP` | 建议量超出本店线路容量 | 阻断，需拆单或人工确认 |
| `E_DUPLICATE` | 同店同 SKU 24 小时已有待处理单 | 禁止重复生成 |
| `E_STALE` | 数据快照超 36 小时 | 阻断自动建议，退回手工 |
| `W_STOCKOUT` / `W_SPARSE` / `W_PROMO` | 缺货截断 / 历史不足 / 促销未回传 | 置信度降级或告警 |

### 3.4 调拨评分

```
score = 0.35×富余度 + 0.25×效期紧迫 + 0.20×距离 + 0.10×同城 + 0.10×装载匹配
约束：调出后本店可售库存不得低于安全库存
```

## 4. 演示脚本（约 6 分钟，可直接念或点「自动滚动」）

1. **项目总览**：先看整体——8 店 50 常温 SKU 试点、16 万预算、三处瓶颈（有货≠可售 / 缺货截断 / 配送排队）。
2. **缺货上报**：门店默认「ST001 上海·徐汇社区店」（缺货最多）。系统已识别若干条缺货，其中「账面有货但可售为 0」的条目被标为「有货不可售」。勾选若干条 → 提交上报。
3. **建议审核**：把某一单建议量改掉并填理由（例如「周末园区团建，门店临时加场」）→ 通过下发；其余按建议直接通过。改量不填理由会被拦，理由与改量幅度都进返工分析。
4. **跨店调拨**：DC 中央仓库存不足的单会出现在这里（演示数据里 S001/S003/S014/S027 天然触发）。点「查看调拨建议」→ 按 5 因子评分给出 Top3 → 审批生成调拨单。
5. **到货确认**：自上而下收货，默认按应到数量预填；把某一行实收改成少于应到，会立刻开出「数量差异」异常单——这正是 `01` 里账实差异 8% 的现场来源。
6. **回到看板**：处理时长、返工、采用率随你处理几单实时更新；「延迟归因」柱状图显示约 30% 延迟是配送排队，不是预测问题。
7. **审计日志**：每一步都有操作人、前后值、快照版本，能回答「谁在什么时候把数量从 X 改成 Y、为什么」。

> 演示辅助：右上角「演示引导」分 6 步遮罩带路；「自动滚动」每 3 秒循环切换视图，模拟「每天两次刷新」（retail-f34）；「重置演示数据」清空会话回到初始样本。

## 6. 代码结构与可验证性

```
mvp/
├── index.html   结构（9 个视图容器 + 侧边导航）
├── style.css    样式（浅色、双列布局、移动端折叠）
├── data.js      数据层：确定性生成 8 店 / 50 常温 SKU / 14 天日销 / 库存 / 在途 / DC / 促销
├── engine.js    决策层：纯函数（baseline / detectShortage / suggest / rankTransfers / classifyDelay / kpi / shouldFallback）
└── app.js       交互层：状态管理、视图渲染、事件、审计、引导、自动滚动
```

`engine.js` 无 DOM 依赖，可直接用 Node 验证：

```bash
node -e "require('./data.js');require('./engine.js');
const D=RC_DATA,E=RC_ENGINE;
console.log(E.suggest(D,'ST001','S001',{}));
console.log('门店',D.stores.length,'SKU',D.skus.length,'角色',D.roles.length);"
```

已用无头浏览器跑过一次完整端到端：上报 → 改量下发 → 调拨审批 → 收货 → 看板与审计更新，控制台零报错。

## 7. 与真实系统的差距（已知限制，必须写明）

| 差距 | 影响 | 真实项目需要 |
|---|---|---|
| 数据为合成样本，存 localStorage | 无法多端协同、无并发控制 | 真实 POS/WMS 接口 + 服务端数据库 |
| 无登录与角色鉴权 | 权限矩阵只是界面层演示 | 统一身份 + RBAC + 操作审计入库 |
| 建议量用近 7 日简单均值，无促销/天气因子 | 促销期和大促前后偏差大 | 促销日历、天气、节假日特征 |
| 无预测模型 | 新品与突变需求仍靠品类均值兜底 | C 档范围（`05-报价单.xlsx`） |
| 调拨不含车辆装载与线路优化 | 可能增加物流成本 | 与 TMS 打通或人工二次确认 |
| 异常单只在本地生成 | 不进入工单系统 | 对接客服/工单平台 |

这些差距在 `04-设计方案.md` 的风险表中均有对应缓解措施，不属于「演示后才发现」的问题。
