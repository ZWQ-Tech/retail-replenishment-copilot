# 门店补货与库存协同 · FDE 交付仓库

> 项目：门店补货与库存协同（合成业务场景）
> 企业：拾光连锁（48 家门店 · 华东三城，试点 8 店 × 50 常温 SKU）
> 来源：FDE 训练中心 · 业务挖掘阶段的实验室成果
> 版本：v2.0 · 2026-11-06

## 一句话结论

48 家门店「一边缺货、一边积压」的根因不是缺预测模型，而是**缺货信号靠微信群传递、补货量靠人工 Excel 估算、跨店调拨靠电话协调**这三段手工环节。调研收敛后，最值得先做的不是销量预测，而是**「可售库存口径与缺货标识」治理**（账实差异平均 8%，销量为零可能是缺货截断）。建议先做「缺货识别 → 规则化建议量 → 例外人工复核 → 一键下发/调拨」的最小闭环，试点 8 店 50 常温 SKU、6 周，把缺货率从 12% 压到 5% 以下、周转从 48 天降到 35 天。

## 现状基线与试点目标

| 指标 | 现状（人工期） | 试点目标 | 口径 |
|---|---|---|---|
| 爆款缺货率 | 12% | 5% 以下 | SKU-店·日维度（retail-f00） |
| 库存周转 | 48 天 | 35 天 | 平均库存成本 ÷ 日均销售成本（retail-f00） |
| 账实差异 | 平均 8% | 待定 | 每日盘点 20 个重点 SKU（retail-f12） |
| 延迟补货归因 | 约 30% 源于配送排队 | 先核查截单时间 | 延迟补货单抽样（retail-f51） |
| 报废 | 待补基线 | 不增加 | 报废成本 ÷ 销售额，促销期单列（retail-f42） |

> 试点范围：8 家门店 × 50 个常温 SKU × 6 周，预算 16 万元（retail-f02/f03/f05）。口径与 `docs/01-业务挖掘.md` 第 2 节完全一致。

## 本地运行与复现

```bash
# 打开 MVP（直接双击也可）
python3 -m http.server 8000     # 然后访问 http://127.0.0.1:8000/mvp/

# 验证规则引擎（无 DOM 依赖）
cd mvp && node -e "require('./data.js');require('./engine.js');
const D=RC_DATA,E=RC_ENGINE; console.log(E.suggest(D,'ST001','S001',{}));"

# 重新生成流程图与报价单
python3 tools/gen_flow.py
python3 tools/gen_quote.py
```

## 边界声明

本项目为**合成业务场景**，仅使用训练项目提供的资料口径；人物、门店、单据均为合成样本。所有真实接口（POS、WMS、ERP）、真实业务验收与真实客户签核需另行核实。MVP 不写入任何真实业务系统、不自动批准补货或调拨，所有不可逆动作前均设有确定性校验与具名人工确认节点。
