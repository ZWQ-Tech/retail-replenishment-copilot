# 门店补货与库存协同 · FDE 交付仓库

> 项目：门店补货与库存协同（合成业务场景）
> 企业：拾光连锁（48 家门店 · 华东三城）
> 来源：FDE 训练中心 · 业务挖掘阶段的实验室成果
> 版本：v1.0 · 2026-10-29

## 一句话结论

48 家门店「一边缺货、一边积压」的根因不是缺预测模型，而是**缺货信号靠微信群传递、补货量靠人工 Excel 估算、跨店调拨靠电话协调**这三段手工环节。建议先做「缺货识别 → 规则化建议量 → 例外人工复核 → 一键下发/调拨」的最小闭环，把单均处理时长从 4.2 小时压到 40 分钟以内，再谈销量预测模型。

## 报价概览

| 方案 | 范围 | 周期 | 含税总价 |
|---|---|---|---|
| A 档 · 试点版 | 3 店 / 12 品类 | 12 周 | **301,000 元** |
| B 档 · 标准版 | 48 店全量 + 调拨协同 | 20 周 | **656,000 元** |
| C 档 · 进阶版 | 48 店 + 需求预测模型 + 供应商 VMI | 32 周 | **1,254,000 元** |

按 `01-业务挖掘.md` 保守估算的年化价值 78 万元计，B 档静态回收期约 10 个月，A 档约 5 个月。

## 现状基线与 MVP 实测

| 指标 | 现状（人工期，26 单样本） | MVP 实测 | 试点目标 |
|---|---|---|---|
| 单均处理时长（上报→下发中位数） | 4.2 小时 | < 1 分钟 | ≤ 40 分钟 |
| 单均返工次数（改量/驳回） | 1.7 次 | 0.25 次 | ≤ 0.5 次 |
| 单据版本正确率（应到 vs 实收） | 82% | 100%（3 单） | ≥ 96% |
| 建议采用率 | 未统计（数据缺口） | 75% | ≥ 70% 并建立基线 |
| 人工复核成本 | 63 元/单（4.6 万元/月） | 14 元/单 | 降 50% |

> MVP 数值来自单次演示会话（4 单），样本量小，只说明变化方向；口径与 `docs/01-业务挖掘.md` 第 2 节完全一致。

## 本地运行与复现

```bash
# 打开 MVP（直接双击也可）
python3 -m http.server 8000     # 然后访问 http://127.0.0.1:8000/mvp/

# 验证规则引擎（无 DOM 依赖）
cd mvp && node -e "require('./data.js');require('./engine.js');
const D=RC_DATA,E=RC_ENGINE; console.log(E.suggest(D,'ST001','S001',{}));"

# 重新生成流程图与报价单
python3 tools/gen_flow.py
python3 tools/gen_quote.py
```

## 边界声明

本项目为**合成业务场景**，仅使用训练项目提供的资料口径；人物、门店、单据均为合成样本。所有真实接口（POS、WMS、ERP）、真实业务验收与真实客户签核需另行核实。MVP 不写入任何真实业务系统、不自动批准补货或调拨，所有不可逆动作前均设有确定性校验与具名人工确认节点。
